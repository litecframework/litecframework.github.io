Event-driven C web framework

Build web apps.
Keep C simple.

liteC is a lightweight C web framework with an epoll-based event-driven HTTP engine, non-blocking connections, WebSockets and a worker pool—wrapped in concise route declarations and practical application helpers.

Framework architecture & status

Current development direction: event-driven HTTP with optional worker offloading.
The current unified development build brings the epoll server, HTTP application helpers, WebSockets and worker support together. Check the exact header revision you ship before relying on optional configuration or extension details.
ComponentCurrent documented capability
HTTP engineLinux epoll event loop, non-blocking sockets and incremental connection handling.
HTTP application APIBlock-style GET() and POST() routes and response helpers.

WebSocketsHandshake and message support, ping/pong, close handling and broadcasting helpers.

The event loop and the worker pool have different jobs. The event loop manages socket readiness and connection state; workers run tasks that should not hold up that loop.

Installation & compilation

Place the unified LiteC header beside your application source and keep runtime directories such as templates/, static/ and uploads/ where the application can access them.

myapp/
├── app.c
├── lite_epoll.h
├── templates/
│   └── index.html
├── static/
│   └── style.css
└── uploads/

Compile with pthread support because the worker-pool build uses threads:

gcc -std=gnu11 -Wall -Wextra -O2 -pthread app.c -o app

Run the application:

./app
The project has been developed and used in Linux and Android/Termux workflows. The documented default listener in the current development build is loopback (127.0.0.1); do not assume it is exposed to other devices on your network.

Quick start

#include "lite_epoll.h"

GET("/") {
    return html("<h1>Hello, LiteC!</h1>");
}

GET("/about") {
    return text("About liteC");
}

run(8080);

Open http://127.0.0.1:8080. The final run(8080) starts the server and enters its event loop.

Use the actual header filename in your project. The examples on this page use lite_epoll.h as the unified event-driven header name; if your checked-out release uses another filename, change only the include.

Event-driven HTTP engine

Earlier blocking server designs accept a client and perform the request/response work synchronously. The event-driven LiteC engine uses Linux epoll to monitor many sockets without dedicating a blocked thread to every connected client.

How the event loop works

  1. The server creates a listening socket and registers it with epoll.
  2. Accepted client sockets are configured for non-blocking I/O and registered with the event loop.
  3. The loop waits for readiness events and processes whichever connections can currently be read or written.
  4. Each connection keeps its own incremental request and response state, allowing partial reads and writes to continue across events.
  5. When a response has been completely written, the connection can be reused or closed according to the HTTP connection state.
Why this matters: many idle or active client connections can be managed by one event loop without a thread blocked on every socket.

Connection capacity

The current development configuration has a default connection capacity of 256 simultaneous connection slots. This is a compile-time/configuration limit, not a promise of a particular requests-per-second figure. Raising it requires checking the matching header's capacity settings and memory requirements.

Event-driven does not mean every route is asynchronous

Route blocks remain ordinary C code and are dispatched synchronously by the event loop. A short handler that validates input and returns a response is straightforward. A handler that sleeps, performs a slow synchronous database operation, or waits on slow file/network I/O holds up the event-loop thread while it runs.

Do not block the event loop. Keep route handlers short. Move slow or blocking work to the worker facility, then return its result to the event-loop side using the mechanism supported by the current header. Do not call LiteC request/response APIs from a worker thread unless the framework explicitly documents that operation as thread-safe.

Worker pool & blocking operations

LiteC combines event-driven socket handling with a worker pool. The event loop remains responsible for network events; workers handle tasks that may take time or block.

Start with the default event loop

run(8080);

Start with an explicit worker count

run_workers(8080, 8);

This example starts the server on port 8080 with a worker pool configured for eight workers in the development API.

Offload slow work with blocking()

blocking() is the worker-offloading facility discussed for moving slow operations away from the event-loop thread. Use the exact callback/signature exposed by the header version you are compiling; do not guess a callback prototype from this overview.

Good worker tasks include slow synchronous database calls, expensive password hashing, CPU-heavy processing and blocking third-party library calls. Keep tasks bounded so a few long-running jobs do not occupy the entire worker pool.

Thread-safety rules

  • Do not access global request/response state from a worker thread.
  • Do not call route response helpers from a worker unless the API explicitly marshals the operation back to the event loop.
  • Pass worker tasks the data they need; avoid pointers to request data whose lifetime may end before the task completes.
  • Keep WebSocket/event-loop callbacks short. Offload expensive work rather than holding up socket processing.
  • Use a sensible worker count for the device and workload; more threads do not automatically mean higher throughput.

WebSockets

The unified event-driven development build includes WebSocket support alongside HTTP. WebSockets upgrade an HTTP connection into a persistent, two-way channel, making them useful for chat, dashboards, live status and interactive applications.

Capabilities

CapabilityDescription
HandshakeHTTP upgrade negotiation to establish a WebSocket connection.
MessagesReceive and send WebSocket messages using the WebSocket API exposed by the header.
Ping/pongProtocol control frames for connection liveness.
Close handlingHandle connection shutdown and cleanup.
BroadcastSend a message to connected WebSocket clients through the broadcast facility.
WebSocket callback names and exact signatures must be copied from the release header. This overview intentionally does not invent callback names. Keep callbacks short and do not perform blocking work directly inside them.

Typical use cases

  • Live notifications and chat.
  • Real-time monitoring dashboards.
  • Device status and telemetry updates.
  • Collaborative or interactive browser applications.

Routing

GET routes

GET("/") {
    return text("Welcome!");
}

GET("/about") {
    return text("About liteC");
}

POST routes

POST("/login") {
    char *username = form_get("username", "");
    char *password = form_get("password", "");

    if (!username[0] || !password[0])
        return text("Username and password required");

    return text("Login request received");
}

Dynamic route parameters

GET("/users/<id>") {
    return text("User ID: %s", param("id"));
}

For /users/42, the route parameter id contains 42.

Templates

Keep HTML files in the templates/ directory.

GET("/") {
    return render("index.html");
}

GET("/profile") {
    return render("profile.html",
        "name", "Usman",
        "role", "Developer");
}

Template values can be displayed with double curly braces:

<h1>Welcome, {{ name }}</h1>
<p>Role: {{ role }}</p>

Template conditions

{% if logged_in %}
    <h1>Welcome back!</h1>
{% else %}
    <h1>Please log in</h1>
{% endif %}
Confirm supported template expressions and escaping behavior against the exact header revision. Never treat untrusted user input as trusted HTML.

Request data

Form fields — form_get()

Use form_get() to read submitted form values. Its two-argument form supplies a fallback value when the field is absent.

POST("/login") {
    char *username = form_get("username", "");
    char *password = form_get("password", "");

    if (!username[0])
        return text("Username required");

    return text("Welcome, %s", username);
}
ExampleMeaning
form_get("username", "")Return the submitted username or an empty string fallback.
form_get("username", "Guest")Return the submitted username or Guest.
form_get("password", "")Read the password field with an empty fallback.

Query strings

GET("/search") {
    return text("Search: %s", query("q"));
}

For /search?q=liteC, the query value is liteC.

Route parameters

GET("/products/<id>") {
    return text("Product ID: %s", param("id"));
}

Form encoding

URL-encoded form fields are available through the form API. Multipart requests are used for browser file uploads. The exact parser limits and supported multipart features are defined by the header build.

Sessions & cookies

Sessions keep user-specific state across requests. Use the session helpers exposed by the framework.

Set a session value

POST("/login") {
    char *username = form_get("username", "");

    session_set("username", username);

    return redirect("/dashboard");
}

Read a session value

GET("/dashboard") {
    const char *username = session_get("username");

    if (!username)
        return redirect("/");

    return text("Welcome, %s", username);
}

Expiry and clearing

session_set("username", username, "-e", 600);

GET("/logout") {
    session_clear();
    return redirect("/");
}

The expiry example requests a 600-second lifetime. Session storage is not a substitute for a persistent database. Use cookie/session settings appropriate for your deployment and HTTPS environment.

CSRF protection

CSRF protection helps prevent a third-party site from causing a user's browser to submit unwanted authenticated requests.

Protected HTML forms

When automatic CSRF integration is enabled in the selected build, supported HTML POST forms receive token integration from LiteC.

<form action="/register" method="POST">
    <input name="username" required>
    <input name="password" type="password" required>
    <button type="submit">Create account</button>
</form>

JavaScript requests

For JavaScript requests, use the CSRF token exposed by the rendered page and send it in the X-Lite-CSRF-Token header when required by the active configuration.

const token = document.querySelector(
  'meta[name="lite-csrf-token"]'
)?.content;

const data = new FormData();
data.append("username", "example");

const response = await fetch("/profile", {
  method: "POST",
  headers: { "X-Lite-CSRF-Token": token },
  body: data
});
Do not manually set the multipart Content-Type when sending browser FormData; the browser must generate the boundary. CSRF enforcement and route exemptions depend on the active header configuration. In the upload-fix build discussed in the project, the upload route is exempted so a basic multipart upload can be submitted without a token; do not assume every LiteC build has that exemption.

Rate limiting

Use the route rate-limit declaration where it is enabled in the current build:

RATE_LIMIT("/login", 5, 60);

POST("/login") {
    char *username = form_get("username", "");
    return text("Login request received");
}

This configures a limit of five requests in a 60-second window for the route, according to the implementation's client tracking and reset behavior.

Confirm the active build's rate-limit identity key, status response and storage limits in the header before deploying it publicly.

File uploads

LiteC's multipart upload helper saves an uploaded file into a destination directory.

HTML form

<form action="/upload" method="POST"
      enctype="multipart/form-data">
    <input type="file" name="file" required>
    <button type="submit">Upload</button>
</form>

POST route

POST("/upload") {
    int saved = 0;

    if (!upload_save("file", saved, "uploads") || !saved)
        return text("Upload failed");

    return text("Uploaded: %s (%zu bytes)",
                upload_name(), upload_size());
}

The first argument to upload_save() is the HTML input name. The second is the status variable used by this API. The third is the destination directory.

HelperPurpose
upload_save("file", saved, "uploads")Save the multipart file field named file.
upload_name()Read the uploaded filename metadata.
upload_type()Read the uploaded content type.
upload_ext()Read the uploaded extension.
upload_size()Read the uploaded file size.

Prepare the destination

mkdir -p uploads
chmod u+rwx uploads
The server process must have permission to write to the destination directory. Match the HTML input name exactly to the name passed to upload_save(). Never trust the original filename, extension or browser-provided MIME type as proof that a file is safe.

Upload validation & security

POST("/upload") {
    int saved = 0;

    if (!upload_save("file", saved, "uploads") || !saved)
        return text("Upload failed");

    if (upload_size() > 2 * 1024 * 1024)
        return text("File too large");

    if (strcmp(upload_ext(), "png") &&
        strcmp(upload_ext(), "jpg") &&
        strcmp(upload_ext(), "jpeg"))
        return text("Unsupported file extension");

    return text("Upload received");
}

This illustrates extension and size checks using the upload helpers. For production, validate the actual file contents/signature as well, generate safe server-side filenames, prevent script execution in upload storage and consider storing private files outside the public web root.

Complete HTTP application example

This example demonstrates the concise route API, form handling, sessions and the event-driven server entry point. It does not include worker or WebSocket callbacks because those require the exact callback signatures from the chosen header version.

#include "lite_epoll.h"

GET("/") {
    return render("index.html");
}

POST("/login") {
    char *username = form_get("username", "");
    char *password = form_get("password", "");

    if (!username[0] || !password[0])
        return text("Username and password required");

    session_set("username", username);
    return redirect("/dashboard");
}

GET("/dashboard") {
    const char *username = session_get("username");

    if (!username)
        return redirect("/");

    return render("dashboard.html", "username", username);
}

POST("/logout") {
    session_clear();
    return redirect("/");
}

run(8080);

templates/index.html:

<h1>LiteC Login</h1>
<form action="/login" method="POST">
  <input name="username" required placeholder="Username">
  <input name="password" type="password" required>
  <button type="submit">Login</button>
</form>

templates/dashboard.html:

<h1>Welcome, {{ username }}</h1>
<form action="/logout" method="POST">
  <button type="submit">Logout</button>
</form>

Performance & application best practices

  • Keep ordinary route handlers short because they execute on the event-loop thread.
  • Use the worker pool for slow blocking operations; do not block the event loop with sleeps or synchronous long-running work.
  • Do not access request/response globals from worker threads unless the API explicitly supports it.
  • Compile worker-enabled applications with -pthread.
  • Keep WebSocket callbacks short and use the worker facility for expensive processing.
  • Use form_get("field", "") for submitted form values.
  • Keep templates in templates/ and static assets in the configured static directory.
  • Prepare upload directories and validate uploaded content.
  • Use CSRF protection for authenticated browser POST requests except for deliberately configured exemptions.
  • Use rate limiting on login, registration and other sensitive routes.
  • Preserve the simple GET(), POST() and run(port) application style.
